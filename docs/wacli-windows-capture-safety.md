# Windows WACLI capture: why the safety block stays

**The source-capture blocker is not resolved. No new Windows capture command is enabled.** The SQLite backup API can preserve committed WAL data for one database, but that alone cannot establish a complete account snapshot. The safe fallback is to retain both Windows backup guards, document the missing protocol, and add reproducible synthetic evidence—not relax a guard to produce an apparently successful backup.

This is source-capture work only. Normal Linux installation, offline staging, Windows archive layout, profile selection, migration and media-path mapping are unchanged. No real account, private archive, credentials or live HOME is inspected or modified.

## What the experiments establish

[The synthetic tests](../tests/test_wacli_windows_snapshot_evidence.py) use only new temporary databases and extracted PowerShell guard functions. They never execute a backup script as a program.

| Experiment | Result and limit |
| --- | --- |
| Copy only a base file while committed rows remain in WAL | The copied database passes `integrity_check` but loses all 96 committed fixture rows. Structural integrity is not completeness. |
| Read-only SQLite online backup | All 96 rows and their binary payload digests survive; schema definitions, migration row and `user_version` survive. The test keeps the source WAL present. |
| Commit a new row between incremental backup steps | The completed backup contains all 97 committed fixture rows. This controlled finite mutation does not prove termination under an indefinitely busy writer. |
| Back up two databases separately around ordered updates | Both outputs pass integrity checks, but their combined epochs never existed together at the source. Per-database consistency is not a shared snapshot boundary. |
| Valid schema/version numbers without a producer receipt | They survive backup but cannot identify which WACLI binary produced the store. |
| URI-sensitive filename, missing file, embedded NUL | Literal filename is preserved; read-only missing-file open fails without creating a database; NUL input fails. These are SQLite API experiments, not a deployed Windows path validator. |
| Unreadable source database or WAL | Both fail under an unprivileged POSIX runner; no immutable fallback is attempted. This does not test Windows ACL/share-mode behavior. |
| Windows guard sees real uncheckpointed WAL plus version metadata | Both capture guards still reject; the WAL bytes are unchanged. Merely adding version fields does not unlock capture. |
| Directory enumeration raises permission denial | Both guard functions propagate failure, not success. The permission error is injected into the AST-isolated PowerShell harness. |
| Native capture with or without `--quiesced` | Refuses before source/destination inspection or provider loading, regardless of dependency availability. |
| Private unverified preparation through the existing AES envelope | Exact synthetic original-file bytes and unverified receipt survive; wrong password and modified authentication bytes fail. This uses only `WacliPreparation/v1/`, not native state or publishable Windows capture. |

These tests are evidence for keeping the blocker. They do **not** implement or certify a Windows SQLite snapshot or encrypted Windows capture. Native capture tests now prove unconditional no-I/O refusal; offline export uses directly constructed synthetic ZIP fixtures. AES preparation tests require optional `pyzipper`; a skipped test is not an encrypted round-trip pass. End-to-end Windows encryption/decryption and integrity verification remain untested here.

## Why the existing paths cannot be reused unchanged

[SQLite documents](https://www.sqlite.org/wal.html) that WAL is persistent database state and separating it from the database can lose committed transactions. Its [online backup API](https://www.sqlite.org/backup.html) produces a consistent individual database, can restart after another connection writes, and may never finish under repeated writes. Python exposes that API as [`Connection.backup`](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup). Do not use a bare file copy, SQL dump that filters unknown objects, a source checkpoint, or an `immutable=1` retry against a mutable source.

The reviewed [WACLI v0.15.0 source](https://github.com/openclaw/wacli/tree/a020de724180d31eccfa5241d45443402d62fb06) opens `wacli.db` and `session.db` independently (`internal/app/app.go`, `internal/wa/session.go`). `wacli.db` enables WAL in `internal/store/db.go`. Its Windows `LOCK` uses `LockFileEx` on one byte (`internal/lock/lock_windows.go`); that coordinates cooperating processes, not every SQLite/media writer. It is not a cross-database transaction. The target WACLI/whatsmeow install declarations are not evidence of the producer of an old store.

[backup.ps1](../backup.ps1) currently excludes `*.db-wal`, `*.db-shm` and `*.db-journal` from ordinary embedded secret copies, and its generic robocopy wrapper can warn and continue after locked-file skips. [backup-secrets.ps1](../backup-secrets.ps1) also has a skip-tolerant generic copy wrapper. Its inner `tool-secrets.zip` is plaintext staging; publication applies the existing AES-256 outer envelope. Those generic wrappers must **not** be used for a new lossless WACLI capture. Their behavior is unchanged in this fallback.

Existing VSS helpers request a `ClientAccessible` shadow for a selected volume and can fall back to a direct copy. They neither establish approved multi-volume membership nor prove WACLI application quiescence. [Microsoft's VSS overview](https://learn.microsoft.com/en-us/windows/win32/vss/overview-of-processing-a-backup-under-vss) describes requester/writer coordination and I/O freezing; a successful shadow creation alone is not evidence of that application protocol. A complete same-volume crash-consistent image might be a viable raw SQLite source after recovery on a private copy, but this path needs Windows tests and cannot be asserted from a Linux mock.

## The implementation contract before capture can be enabled

The following is a **proposed v1 contract**, not a format emitted or accepted by current code. Preserve the current archive paths; put an additive versioned capture receipt inside the encrypted `tool-secrets.zip`. Do not reinterpret legacy archives as v1 or treat a hand-written receipt as proof. If restoring a receipt requires a new reader, make that version gate explicit and fail closed.

1. **Approve the full input set.** Require explicit canonical local Windows roots and the exact binary artifact/build evidence. Inventory the profile tree, both databases, original sidecars, unknown files, config and media without exclusions. Resolve configured/legacy/external stores only from explicitly approved inputs; fail if a referenced input is missing or outside approval. Reject ambiguous drive-relative, UNC/network SQLite, ADS/device, traversal, case-colliding and reparse-point paths; prove source/output separation. Do not discover or traverse live HOME by default. Paths and profile metadata remain private encrypted content.
2. **Establish one capture boundary.** Prefer online backup APIs only after a documented, verifiable all-writer quiescence protocol held across both databases, metadata and media. Test compatibility with the exact Windows upstream lock range and sharing modes, but do not mistake that lock for exclusion of non-cooperating writers. Otherwise use a tested coordinated VSS snapshot set covering every approved volume, including every raw WAL/journal and media file. Record whether consistency is application-consistent or crash-consistent; fail if the requested guarantee cannot be established. No direct-copy fallback, source checkpoint, sidecar deletion or `immutable` retry.
3. **Preserve originals and create derived snapshots separately.** Keep every raw source byte, including unknown files and WAL, from the same established boundary. On a private staged copy, use the SQLite backup API to create separate derived complete databases; include all tables, indexes, triggers, FTS/shadow tables and unknown schema objects. Recover hot journals only on staged copies. Do not substitute the derived database for the original bytes. Finite deadlines, busy/locked/error handling, missing WAL/read permission, disk exhaustion, changing inputs and incomplete copy must fail before publication.
4. **Record evidence, not guessed versions.** The encrypted v1 receipt needs capture method/boundary and completion status; tool version and artifact hash; approved input membership and complete file sizes/hashes; source binary hash and attested build/commit/module evidence, including whatsmeow and SQLite driver; SQLite engine/build options used for the snapshot; full schema definitions/digest and `schema_migrations` rows for `wacli.db`; `whatsmeow_version` rows for `session.db`; and relevant SQLite `user_version`, `application_id`, `schema_version`, page size and journal mode. Read schema information only on staged snapshots, never chat/session-key rows for metadata. Validate types, bounded sizes, known receipt version and required fields. Refuse malformed/unsupported versions. An observed binary version at capture time is **not** historical producer provenance; unknown producer remains an explicit blocker rather than adopting the Linux target pin.
5. **Use the existing encrypted secret workflow, strictly.** Keep `mainframe-secrets.zip` containing encrypted `tool-secrets.zip` with WinZip AES-256; do not create an alternative plaintext export. Restrict staging ACLs, require a supported encryption provider, treat every nonzero copy/archive warning as failure for this capture, decrypt/authenticate and byte-hash-verify every staged member before publication. Test incorrect password, modified ciphertext, truncated output and missing provider. Only publish a new complete artifact after verification; never replace a private existing archive. Logs contain only fixed diagnostics/counts, not SQL, profile paths, receipt contents, passwords or payload values. Preserve the existing vault lookup; this task does not access it.
6. **Prove the Windows implementation with synthetic fixtures.** Required acceptance tests include both actual Windows database/WAL ACL denial and sharing violations; store lock contention; stopped/uncooperative writers; coordinated two-database/media mutation; raw WAL recovery; rollback journals; schema/version receipt rejection; malformed/reparse paths; missing SQLite/encryption tools; busy timeout; disk-full and copy failure; and authenticated encrypted round-trip with exact byte equality. A Linux SQLite experiment or mocked VSS/ACL response is not a substitute for those Windows tests. Install/run no real WACLI account as part of these tests.

## Exact outcome and next gate

**Capture coverage added: none.** Both Windows guards remain unchanged; no database, WAL, external store or version receipt is newly captured. Existing formats remain backward-compatible because this change only adds tests/documentation.

The next implementation needs a synthetic Windows test environment with the required existing SQLite and AES archive dependencies, plus an agreed verifiable capture boundary/provenance policy. Until that exists, this is a safe blocked result, not the first successful full source backup.

Even after that gate passes, [the remaining migration gaps](linux-wacli-windows-parity.md) remain: complete schema compatibility, Windows account/config selection, external media preservation and path mapping, non-overwriting activation, and functional local/search/media/linked-device validation. None is performed or claimed here.

The subsequent [snapshot preparation milestone](wacli-snapshot-preparation.md) adds a private staged SQLite engine and candidate AES integration, with a no-I/O blocked public preflight. It does not implement a boundary backend, accept a trusted capture receipt, change either Windows guard, or establish Windows validation. The proposed v1 capture contract above remains unimplemented.

## Stop/copy/restart assessment: attestation bypass removed

The legacy `wacli_state.py capture --quiesced` route and its `snapshot()` API previously allowed caller attestation plus cooperative Unix locks to authorize copying. They now refuse unconditionally before reading either path, loading encryption, asking for a password or creating output. This removes an alternate capture route; it does not implement a Windows stop backend. Existing offline export remains available without certifying historical capture consistency.

`whatsapp-account.ps1` starts authentication in a detached PowerShell process and dispatches arbitrary commands without a registered service/process owner, verified clean-close protocol or launch-exclusion gate. The backup scripts do not supply those controls, and their generic skip-tolerant copies are not a lossless capture boundary. Unknown writers and independent SQLite/media handles cannot be ruled out. Polling for process exit, forced termination, timeout, an absent sidecar or a cooperative lock cannot repair that gap.

No processes or services are stopped, launched or restarted by this change. Future restart must use recorded long-running service identities and restart only services that were running before capture, never replay one-shot commands. Failed close, forced termination, timeout, unknown writers, sidecars and unproven exclusion must block copying. See [the current native state contract](linux-wacli-state.md). Capture remains disabled; complete Linux restoration remains unfinished.

The [Windows stop/copy/restart coordination assessment](wacli-windows-stop-coordination.md) traces the existing entry points, explains why helper-only coordination cannot fence direct/external writers, and records the minimum enforced storage/launch owner plus producer clean-close contract required before implementation. It adds no coordinator or capture authority.
