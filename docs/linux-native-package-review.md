# Native Linux package review

The planner accounts for every allowlisted package. **Planned means a source and installation route have been mapped, not that anything has been installed or tested at runtime.** Windows application state, credentials, services, browser profiles and shell integration remain separate work. No package is removed merely because it is blocked.

## Newly mapped native tools

These conservative adapters target Debian/Ubuntu **x86_64 with glibc**. Other architectures remain explicit blockers even when upstream offers more builds. Each resolver reads the current authoritative Windows manifest and requires the corresponding official Linux product, version and variant. Missing, ambiguous or changed metadata blocks the action; it never falls back to a different latest version or a distro lookalike.

GitHub asset digests, Node's checksum file over HTTPS, and npm integrity metadata are checksum sources, **not independently verified release signatures**. These adapters do not claim GPG/npm-signature verification. Release data and checksums are resolved dynamically, never copied from a user's backup into code.

## Future installation is separate and explicit

The default remains a dry plan. It may fetch public manifests, release JSON and checksum text, but not product archives or private state. A separately authorized partial installation would require `--execute --select <name> --native-root <name>=/absolute/new/directory`; repeat `--native-root` for each selected product. There is no default home destination, overwrite or automatic PATH edit. Supplying roots or the existing SDK/AnyDesk consent flags does not turn a dry run into execution or grant consent for another product.

Before any selected changes, validate every required new destination and platform gate. Downloads are bounded and verified before archive handling; archive layout, paths, types, sizes and native ELF headers are checked before publication. Publication reuses descriptor-relative ancestor validation and atomic no-replace helpers from `bitwarden_cli_linux.py`, so changes to those helpers require all native installer regression tests. Source metadata or archive layout drift must fail loudly rather than loosen extraction rules.

The standalone tools do not execute themselves during installation. They do not create services, log in, import Windows state, run npm postinstall, initialize gcloud, edit profiles or install global packages. Tools installed under explicit roots are not automatically available to subsequent package-manager commands; PATH and dependent runtime validation must be reviewed separately. A full restore remains blocked while any required package or Python manifest is unresolved.

## Unresolved products: one review, not substitutions

The dry plan is the authoritative ordered list of exact current names and reasons. These are the source-level findings behind its deliberately retained blockers:

- **Windows-only exact products:** `bulk-crap-uninstaller`, `dark`, `ditto`, `innounp`, `micmute`, `rufus`, `sysinternals`, `vcredist-aio`, `windows-terminal`, `winfsp-np`, `GPSoftware.DirectoryOpus`, `StartIsBack.StartAllBack`, and `Tonec.InternetDownloadManager`. Keep their declarations and explicit blockers. See [BCU](https://www.bcuninstaller.com/), [Ditto](https://ditto-cp.sourceforge.io/), [Rufus](https://rufus.ie/), [Sysinternals](https://learn.microsoft.com/en-us/sysinternals/), [WinFsp](https://winfsp.dev/), [Directory Opus](https://www.gpsoft.com.au/), [StartAllBack](https://www.startallback.com/), and [IDM's explicit Linux exclusion](https://www.internetdownloadmanager.com/register/new_faq/functions1.html).
- **Variant or behavior mismatch:** `herdr` uses the repo-local preview fork/channel; do not silently replace it with [upstream stable](https://herdr.dev/docs/install/). `mpv-git` is not [stable mpv](https://mpv.io/installation/). [`nuget.exe`](https://learn.microsoft.com/en-us/nuget/reference/nuget-exe-cli-reference) has no identical native Linux command surface; Mono or `dotnet nuget` is not an implicit replacement. [Parsec for Linux](https://support.parsec.app/hc/en-us/articles/32381552552340-Install-Parsec-App-on-Linux) is client-only, without hosting; Windows role/state is unresolved.
- **Linux exists but integrity/install/state work remains:** [`discord`](https://discord.com/download), [`gcloud`](https://docs.cloud.google.com/sdk/docs/install-sdk), [`ngrok`](https://ngrok.com/download/linux), [`pwsh`](https://learn.microsoft.com/en-us/powershell/scripting/install/linux-overview), [`steam`](https://store.steampowered.com/about/), [`tor-browser`](https://www.torproject.org/download/), [`Windscribe.Windscribe`](https://windscribe.com/knowledge-base/articles/how-to-set-up-windscribe-on-linux), and [`Wakatime.DesktopWakatime`](https://wakatime.com/linux). Each needs a validated pinned source/integrity and installation contract, with distro dependencies, signatures or service/identity handling where relevant. Public Linux availability alone is not a completed adapter.
- **`vscode`:** official Microsoft [Linux builds](https://code.visualstudio.com/docs/setup/linux) and [checksums](https://update.code.visualstudio.com/api/update/linux-x64/stable/latest) exist, but [download/use is subject to vendor terms](https://code.visualstudio.com/download). No consent is inferred from the user's SDK/AnyDesk authorization. No native installer or Windows-state migration is validated here.
- **`pip-freeze.txt` — superseded historical review:** an older supplied backup may retain this legacy file as restore control metadata, but it is excluded from user data and the Linux planner ignores it with no action or blocker. The automatic frozen snapshot is retired; Windows Full no longer installs it. Explicit repository-only `requirements.txt`/`requirements-linux.txt` files remain planning-only, with generic execution blocked pending preflight.

**ngrok metadata-only update:** the explicit dry-plan option now cross-checks the current Scoop Windows x64 version and checksum against ngrok's same-version stable archive-index row and records the Linux x86_64 candidate URL/SHA-256. This remains a live metadata observation, not a restore pin or artifact verification; the archive layout, bounded extractor, and installation route are still blocked. See the [ngrok metadata review](linux-ngrok-metadata-review.md).

**PowerShell metadata-only update:** the explicit dry-plan option matches the current Scoop version and Windows x64 URL/hash to the official GitHub release tag, exact Windows/Linux x64 asset URLs, and published checksum rows. The 2026-10-24 observation was `7.6.8`; this is not a restore pin, and no package archive is downloaded. Scoop script/persistence fields are ignored as untrusted data. Archive layout, safe extraction, and distribution-specific PowerShell/.NET dependencies remain unvalidated, so installation and Windows profile/module import stay blocked. See the [PowerShell metadata review](linux-pwsh-metadata-review.md).

## Existing cross-platform declarations

Existing native APT mappings and package-manager declarations remain accounted for, not upgraded into runtime-validation claims. [`@googleworkspace/cli`](https://github.com/googleworkspace/cli) now has a separate [official native archive adapter](linux-google-workspace-cli.md): exact registry version, matching stable release, GitHub SHA-256/size and verified companion checksum, bounded archive parsing and explicit new `--gws-root`. It avoids the npm wrapper entirely rather than suppressing its downloader scripts; Node/pnpm are not required or invoked. CLI execution and account/Windows-state activation remain untested and unauthorized. [`vercel`](https://vercel.com/docs/cli) documents pnpm installation; [`graphifyy`](https://pypi.org/project/graphifyy/) documents Linux and `uv tool install`; [`wacli`](https://github.com/openclaw/wacli) documents Linux, Go/cgo and SQLite FTS5 builds. WACLI is now a planned `standard-linux-go-install` dry-plan item: normal explicit GOBIN or first GOPATH/bin (normally `~/go/bin`) and normal module/build caches, with no portable/isolated HOME requirement. Vercel and graphifyy still require isolated destination validation of their pinned-version build requirements, interpreter/toolchain versions, PATH, optional install scripts and authentication. WACLI host/toolchain/native prerequisite and integrity preflights remain unperformed; see [its exact dry-plan review](linux-wacli-build-review.md). Newly mapped native pnpm/uv do not prove their dependent global applications are operational.

Independent review also found the inherited global-tool commands did not preflight their interpreters, native build dependencies, install-script policy or destinations. Consequently `vercel` and `graphifyy` remain **explicitly blocked** in the dry plan, while the declared WACLI build is **planned but categorically non-executable before adapter preflight**; upstream Linux support does not imply testing or installation. Original names, versions/tags and proposed commands remain visible; nothing is removed or installed. A compatible Python manifest would likewise remain blocked until an explicit isolated venv/interpreter/dependency contract is implemented. Generic global actions, including a hand-built pnpm action for Google Workspace, cannot bypass this gate or cause earlier selected actions to mutate the machine. APT executable availability and every candidate are checked before any selected installation.
